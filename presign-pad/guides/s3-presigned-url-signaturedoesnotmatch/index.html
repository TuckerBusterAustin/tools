How to fix SignatureDoesNotMatch on an S3 presigned URL

What the error means

When you use a presigned URL, S3 rebuilds the signature from the request it actually received and compares it with the X-Amz-Signature in the URL. SignatureDoesNotMatch means the two differ. Either the secret key is wrong, or the request S3 received is not the one that was signed. Usually it's the second.

The good news is that S3 tells you what it computed. The error body looks roughly like this:

`xml

<Error>

<Code>SignatureDoesNotMatch</Code>

<Message>The request signature we calculated does not match the signature you provided...</Message>

<AWSAccessKeyId>AKIA...</AWSAccessKeyId>

<StringToSign>AWS4-HMAC-SHA256

20261016T120000Z

20261016/us-east-1/s3/aws4_request

9f2c...</StringToSign>

<SignatureProvided>3b1a...</SignatureProvided>

<CanonicalRequest>PUT

/uploads/report%20final.pdf

X-Amz-Algorithm=AWS4-HMAC-SHA256&amp;...

content-type:application/pdf

host:my-bucket.s3.us-east-1.amazonaws.com

content-type;host

UNSIGNED-PAYLOAD</CanonicalRequest>

</Error>

`

The CanonicalRequest is S3's view of your request. To find the problem, compare it line by line with the canonical request your code signed.

Step 1: Read the canonical request S3 built

A SigV4 canonical request has six parts, one per line:

1. HTTP method (GET, PUT, ...)

2. Canonical URI (the URL-encoded object path)

3. Canonical query string (every query parameter except X-Amz-Signature, sorted)

4. Canonical headers (name:value, lowercase, one per line, then a blank line)

5. Signed headers (content-type;host)

6. Payload hash (for presigned S3 URLs, usually UNSIGNED-PAYLOAD)

To get your side of the comparison, log the canonical request when you generate the URL. Most SDKs can print it with debug logging turned on. Then diff the two. The first line that differs is almost always the cause.

Step 2: Check the usual suspects

These are the most common causes, roughly in order of how often they come up:

  • Wrong HTTP method. A URL signed for GetObject fails with PUT, and the reverse is true too. The first line of the canonical request shows the method. AWS's own troubleshooting article lists this first.
  • Headers that differ from the signed ones. If content-type is in the signed headers, the upload must send exactly that Content-Type. Browsers and HTTP libraries often add or change it, for example to application/octet-stream or by adding ; charset=utf-8. Either sign without the content type or send exactly the value you signed.
  • Region mismatch. The credential scope (20261016/us-east-1/s3/aws4_request) must name the region the bucket is in. Signing for us-east-1 against a bucket in eu-west-1 fails.
  • A different host. The host: line must match the host the request went to. Watch out for virtual-hosted vs path-style URLs, custom domains, CDNs and proxies. Classmethod has documented presigned URLs for brand-new buckets failing for a while because a redirect changed the host.
  • Key encoding. Spaces, +, %, and non-ASCII characters in object keys get encoded differently by different tools. Compare the canonical URI line: report%20final.pdf and report+final.pdf are different paths.
  • The URL was changed after signing. A framework, logger or email client may re-encode the query string, add a tracking parameter, or decode %2F. Any change to a signed parameter breaks the signature.
  • Missing session token. If you signed with temporary credentials (a role, SSO, Lambda, EC2), the URL must carry X-Amz-Security-Token.
  • Wrong secret. If the canonical requests match exactly but the signature still differs, check the secret key. Look for a trailing newline or space from copying it out of a file or console, or keys from a different profile.

Step 3: If the canonical requests match

If the canonical request is identical on both sides, compare the StringToSign:

`

AWS4-HMAC-SHA256

<X-Amz-Date, e.g. 20261016T120000Z>

<date>/<region>/s3/aws4_request

<hex SHA-256 of the canonical request>

`

If that matches as well, the only thing left is the signing key, which comes from the secret, date, region and service. That points to the wrong secret, or to a secret that doesn't belong to the AWSAccessKeyId shown in the error.

Pitfalls

  • Don't "fix" the error by making the URL longer-lived or the bucket public. Neither changes the signature.
  • Test with curl before debugging browser code. curl -X PUT -T file.pdf -H "Content-Type: application/pdf" "<url>" sends only what you tell it to. If curl works and the browser fails, the browser is changing a header.
  • Remember that &amp; in the XML is just an escaped &. Unescape it before you diff.
