How to fix SignatureDoesNotMatch on an S3 presigned URL

What the error means

A presigned URL carries its signature in the query string: X-Amz-Algorithm, X-Amz-Credential, X-Amz-Date, X-Amz-Expires, X-Amz-SignedHeaders and X-Amz-Signature. When S3 receives the request, it builds the signature again from what you actually sent. If its result differs from X-Amz-Signature, you get SignatureDoesNotMatch.

The signature itself is almost never the problem. The problem is that the request you send isn't the request that was signed. Work through the causes below in order. The first two cover most cases.

Step 1: Test the URL in isolation with curl

Take your browser, frontend code and upload library out of the picture first. Copy the URL exactly as it was generated and wrap it in single quotes so the shell doesn't touch the & characters:

`bash

curl -v 'https://my-bucket.s3.us-east-1.amazonaws.com/report.pdf?X-Amz-Algorithm=...&X-Amz-Signature=...'

curl -v -X PUT --upload-file ./report.pdf \

-H 'Content-Type: application/pdf' \

'https://my-bucket.s3.us-east-1.amazonaws.com/report.pdf?X-Amz-Algorithm=...'

`

If curl works and your app doesn't, the URL is fine. Your client is changing the request.

Step 2: Check the signed headers

Open the URL and read X-Amz-SignedHeaders. Every header listed there must be sent, with the same value used at signing time. A presigned URL holds only the host, path and query parameters, so S3 can't fill in a header you forgot to send.

The most common case is Content-Type on PUT uploads. If your server passed ContentType: 'image/png' when it generated the URL, the client must send Content-Type: image/png exactly. AWS's own troubleshooting article calls this out (AWS re:Post). Watch for these cases:

  • fetch or axios adding Content-Type automatically when you pass a Blob, File or JSON body.
  • multipart/form-data uploads. A presigned PUT expects the raw file bytes as the body, not a form.
  • Charset suffixes such as text/plain;charset=UTF-8 when you signed text/plain.
  • Signing with content-length or content-md5 and then sending a different body.

The fix: either send exactly the signed value, or stop signing that header and let the client send whatever it wants.

Step 3: Check that the URL arrived intact

The signature covers the path and query string byte for byte. These all break it:

  • Decoding or re-encoding the URL, for example turning %2F into / or + into a space in the object key.
  • Template engines or JSON serializers that escape & as &amp; or &.
  • Proxies, CDNs or link-preview tools that rewrite or reorder query parameters.
  • Keys with spaces or non-ASCII characters that were encoded differently at signing and at request time.

Log the URL right after generation and again right before the request, then diff the two.

Step 4: Check region, endpoint and credentials

  • Region. The region in X-Amz-Credential (for example .../20261016/eu-west-1/s3/aws4_request) must match the bucket's region. For Regions launched after March 20, 2019, AWS says you must specify the Region and endpoint explicitly when signing (AWS CLI reference).
  • Endpoint style. Signing for a virtual-hosted URL and then calling a path-style one (or the reverse) changes the canonical request.
  • Keys. A wrong secret key or a stale session token gives the same error. If you signed with temporary credentials, X-Amz-Security-Token must be present.

Step 5: Check time and expiry

Expiry problems usually show up as AccessDenied with "Request has expired" rather than a signature mismatch, but check them anyway:

  • X-Amz-Date plus X-Amz-Expires (in seconds) must still be in the future.
  • With the AWS CLI or SDKs, the maximum lifetime is 7 days (604800 seconds). In the S3 console it is 12 hours (AWS docs).
  • A URL signed with temporary credentials (an IAM role or STS) stops working when those credentials expire, even if X-Amz-Expires is longer.
  • The signing machine's clock must be accurate. AWS lists clock sync as one of its checks.

Generate a known-good URL to compare against

When you're stuck, generate a URL with the AWS CLI and try it:

`bash

aws s3 presign s3://my-bucket/report.pdf --expires-in 3600 --region us-east-1

`

This presigns a GET only. If the CLI URL works and yours doesn't, compare the query parameters one by one. The difference usually points straight to the cause.

Quick checklist

1. Does it work in curl with the URL quoted? If yes, your client is the problem.

2. Are all headers in X-Amz-SignedHeaders sent with identical values?

3. Is the URL byte-for-byte identical to what was generated?

4. Do the region and endpoint style match the bucket?

5. Are the URL and the signing credentials both still valid?
